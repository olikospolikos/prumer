SKILL.mdThe skill itself. Rules, defaults, and the APP_SPEC template.

Mobile app spec

Convert a fuzzy app idea into a spec a coding agent can build from without stopping to ask questions. The output is a single APP_SPEC.md file. A build session should be able to read it top to bottom and start shipping.

The failure mode this skill prevents: a coding agent that gets a one-line idea, invents its own scope, picks a random stack, and builds the wrong thing. Every decision the spec leaves open is a decision the build agent makes blindly.

Core principle

Decide, don't offer. A spec full of "you could use X or Y" is not a spec. Make a concrete choice for every decision, give a one-line reason, and mark anything you assumed so the user can correct it. Options belong in the conversation, not in the file.

Workflow

  1. Extract the idea from what the user gave you. Pull out the core action, the user, and the point of the app.
  2. Fill gaps. Ask only what you cannot reasonably assume (see "What to ask"). Batch the questions into one message. Do not interrogate.
  3. Make decisions. Apply the defaults below unless the user's context overrides them. Record assumptions.
  4. Write APP_SPEC.md using the template.
  5. Confirm scope in one short message: the one-line pitch, the stack, and the feature list. Get a yes before building.

If the user says "just build it" or is clearly experienced and impatient, compress this: make defaults, write the spec, note assumptions inline, and start.

What to ask (only if you can't infer it)

  • Who uses it and what is the one job it does for them.
  • The 3-6 things a user must be able to do (the real feature list, not nice-to-haves).
  • Does it need accounts / login, or is it single-user on-device.
  • Does it need a backend / shared data / other people's data, or does everything live on the device.
  • Any specific integration that is core to the idea (payments, maps, camera, push, a named API).
  • Platforms: iOS, Android, or both. Default both.

Everything else — navigation pattern, state management, folder structure, styling approach — you decide. Do not ask the user to choose a state library.

Default decisions

Use these unless the idea or the user says otherwise. State the choice and reason in the spec.

  • Framework: Expo (React Native + TypeScript). One codebase for iOS and Android, fast iteration, works well with a coding agent.
  • Navigation: Expo Router (file-based routing under app/).
  • Shared state: Zustand. Local UI state stays in components.
  • Server state / data fetching: TanStack Query, only if there's a backend.
  • Backend (only if needed): Supabase — auth, Postgres, storage, row-level security in one place. Name Firebase as the alternative and move on.
  • On-device storage: AsyncStorage for small key-value data; SQLite (expo-sqlite) or MMKV when there's real structured/local data.
  • Styling: NativeWind (Tailwind for RN) if the user likes utility classes, otherwise StyleSheet. Pick one and use it everywhere.
  • Payments (if selling): RevenueCat over raw StoreKit/Play Billing.

Do not add a backend, auth, or accounts to an app that doesn't need them. A local single-user utility should stay local.

APP_SPEC.md template

Write the file with these sections in this order. Keep every section concrete. Cut a section only if it genuinely doesn't apply, and say why in one line.

# [App name] — build spec

## Pitch
One sentence: what it is and who it's for.

## Users and the core job
Who opens this and the single thing they came to do.

## Scope
### In scope (v1)
- Feature 1 — what the user can do, described as an action
- Feature 2 …
### Out of scope (v1)
- Explicitly excluded, so the build doesn't drift into it.

## Stack
- Framework: [choice] — [one-line reason]
- Navigation: [choice]
- State: [choice]
- Backend: [choice or "none — fully on-device"]
- Storage: [choice]
- Styling: [choice]
- Other services: [payments/push/maps/etc. or "none"]

## Assumptions
Things I decided without confirmation. Correct any that are wrong.
- …

## Screens
For each screen: name, route, what it shows, what the user can do on it.
- **[Screen]** (`route`) — content; actions; where it navigates.

## Navigation
The structure: tabs / stack / drawer, and which screen is the entry point.

## Data model
Each entity: fields with types, and where it lives (device / backend table).
- **Entity** — field: type, field: type; stored in [location].
Relationships between entities.

## User flows
The main paths, step by step. At least the primary flow end to end.
1. …

## Backend / API
Only if there's a backend. Tables, auth rules, and the operations the app performs (read/write/subscribe). Note any external API and what it's called for.

## Design direction
The default design language is the gamified dark system in `references/design-language.md` — copy the relevant parts (color, type, shape, signature components, motion rules) into this section so the spec is self-contained. Override only if the user asks for a different look. Name the reward moments that get animation and state that the build should follow the apple-design skill for motion.

## Build order
Vertical slices, each one runnable when finished. This is the sequence the build should follow.
1. Project scaffold + navigation shell (empty screens, app runs).
2. [First real feature, end to end].
3. …

## Acceptance criteria
Per feature, the observable check that it works.
- [Feature]: [what you can do / see that proves it works].

## Open questions
Anything genuinely undecided that needs the user, or "none".

Build order matters most

A coding agent builds better in thin vertical slices than in horizontal layers. Order the build so the app runs after step 1 and stays runnable after every step. Each slice should touch UI, state, and data for one feature rather than building all screens, then all state, then all data. Put auth and navigation scaffolding first, then the single most important feature end to end, then the rest.

Self-check before delivering

Before handing over the spec, verify:

  • Every stack line has a concrete choice, not a menu.
  • Every in-scope feature appears in screens, data model, build order, and acceptance criteria. If a feature is named but has no screen or no data, the spec is incomplete.
  • Out-of-scope is not empty. Naming what v1 skips is how you stop scope creep.
  • No backend/auth/accounts on an app that doesn't need them.
  • A fresh build session could read the file and start without asking you anything. If it would have to ask, answer it in the spec first.

Handing off

Write APP_SPEC.md to the project root (or where the user wants it). The spec is meant to be executed: a build can start in the same session, or a fresh Claude Code session can open the file and go. When the user confirms scope, start with build-order step 1.

Reference files

  • references/design-language.md — the default visual and motion system (dark gamified, LOCKED-style). Read it when writing any spec's Design direction section.
  • references/onboarding-funnel.md — the default quiz → plan → paywall onboarding structure. Read it whenever the app has onboarding or a subscription.
  • references/example-spec.md — a full worked spec to match the shape and level of detail.
design-language.mdDefault visual and motion system. Dark, gamified.

Design language — gamified dark (LOCKED reference)

The visual and motion system every spec's "Design direction" section should encode by default. Distilled from the LOCKED / "Lock In" habit app (App Store shots, in-app screenshots, and screen recordings) plus Apple's fluid-interface principles (apple-design skill). When writing a spec, copy the relevant parts into the spec's Design direction section — the build agent reads the spec, not this file.

Feel in one line

Dark, masculine, game-like. A discipline app that borrows game UI (XP, ranks, 3D badges) but stays iOS-native in structure and motion. Duolingo mechanics, darker skin.

Color

  • Background: near-black charcoal with a faint green cast (#0C0F0E). Never pure black, never light mode in v1.
  • Surface / cards: one step lighter (#191E1B), no borders — separation comes from the lightness step.
  • Primary accent: bright mint-emerald (#2EE59D). It is the only functional accent: progress ring, XP values, active tab, CTAs, selection rings.
  • Hero gradient: deep emerald → black, top to bottom, on onboarding and header zones. Subtle dot-grid noise texture on gradient surfaces.
  • Warm orange is reserved for the streak flame (and at most an edge-glow on marketing/hero frames). Never a second UI accent.
  • Text: white primary; ~55% white for secondary; accent green for numbers that matter (XP, level).

Typography

  • System font (SF Pro / platform default), no custom face.
  • Stats are the loudest thing on screen: heavy weight, large size, number in accent green, label lowercase and quiet ("level: 30").
  • Motivational lines are uppercase white over full-bleed photos ("MAKE YOURSELF PROUD").
  • Negative tracking on display sizes, near-zero on body. Hierarchy from weight + size together, not size alone.

Shape and depth

  • Everything rounded: pill buttons, 16–24px card radii, circular icon chips.
  • Depth comes from photorealistic 3D assets (metallic shields, trophies, badges — gold/silver/emerald materials) sitting on flat dark ground. No drop-shadow stacks, no skeuomorphic chrome around them.
  • Soft outer glow on the active progress ring and on selected elements.
  • Locked/inactive items are the same asset dimmed to ~25%, not replaced with placeholders.

Signature components

  • XP ring: large circular progress ring (accent green, rounded caps, glow) wrapped around the current rank's 3D badge; XP fraction centered ("46.400/47.000 XP"); level + rank name below.
  • Top bar: wordmark left, streak flame + count right.
  • Task row: dark card, checkbox left, title white, circular category icon right inside a thin green ring, kebab menu. Completing a task fills the check, pops an "+XP" toast, and animates the ring.
  • Add-task: bottom sheet, not a screen. Title field, category picker with emoji icons, XP value.
  • Leaderboard: 3D podium blocks for top 3, crowned #1 avatar with wing graphic, then list rows — avatar, @handle, level, XP right-aligned in green. "+ Invite Friends" pill top-right.
  • Badge grid: circular slots, 3–4 per row, earned badges full-color 3D, unearned dimmed.
  • Tab bar: 5 items, center item rendered as a highlighted pill/outline.
  • Motivation card: full-bleed photo, big uppercase white text, nothing else.
  • Paywall: dark, feature checklist with green checks, price option cards, one big green CTA.

Motion (apply the apple-design skill during the build)

The spec should name these; the build agent should read the apple-design skill for implementation detail.

  • Springs everywhere, critically damped by default (damping 1.0, response 0.3–0.4). Bounce (~0.8) only where the user's gesture carried momentum — sheet flicks, card throws.
  • Respond on press-down, never on release. Transitions interruptible; sheets track the finger 1:1.
  • Reward moments are the exception to restraint: task completion animates the ring and counts XP up; level-up scales the new 3D badge in with a glow. These get the drama; navigation stays quiet.
  • Respect prefers-reduced-motion: cross-fade rewards instead of spring/scale.

Gamification vocabulary

XP, levels, named rank tiers (e.g. Bronze → Silver → Gold → … → Mythic V), daily streaks, limited badges, friend leaderboard. Copy tone is short, imperative, slightly confrontational ("Lock in or stay weak") — confident, not corporate.

What to avoid

  • Light backgrounds, multi-color accent palettes, gradient text.
  • Flat 2D badge icons where a 3D asset is expected — if 3D assets aren't available yet, use a single placeholder asset consistently and note it as a TODO in the spec.
  • Confetti or celebration effects outside the defined reward moments.
  • Borders and dividers as the primary separation tool; use surface lightness steps.
onboarding-funnel.mdQuiz to plan to paywall onboarding structure.

Onboarding funnel — quiz → plan → paywall

The default onboarding and monetization structure for consumer apps specced by this skill. Distilled from two reference apps (Scratch AI, a golf caddy; Kiku, a language app) that run the same funnel with different skins. When a spec includes onboarding or a subscription, encode this sequence in the Screens, User flows, and Build order sections.

Why this order

Every step earns the next: the quiz personalizes, the interstitials sell, the generated plan creates ownership, social proof de-risks, the commitment pledge raises intent, and only then comes the paywall — with account creation last so no one bounces on a signup form before seeing value.

The sequence

  1. Welcome — hero visual, one-line promise, primary "Get Started", secondary "Sign In". No feature tour.
  2. Quiz — one question per screen, 8–20 steps. Thin progress bar top. Options are full-width rounded rows with a radio circle; selected state = accent ring + check. Continue pinned bottom (disabled until a choice), or auto-advance on single-select. Question types seen: goal, experience level, frequency, self-assessment, biggest weakness, numeric input via ruler/slider, "have you tried other apps".
  3. Value interstitials — every 3–5 questions, a full-bleed dark hero screen with one bold claim tied to what they just answered ("Every pro golfer has a coach and a caddy. Now you do too."). These sell during the quiz, not after it.
  4. Personalized claim — a screen that turns their answers into a concrete promise with a simple chart ("Lowering your handicap by 42 is a realistic goal" + improvement-over-time line). The number comes from their inputs.
  5. Social proof — rating (e.g. 4.8 ★ with laurels), user/lesson counts, 2–3 review cards with names and stars.
  6. Commitment pledge — streak options as rows: 7 / 14 / 50 / 100 days labeled Good / Great / Incredible / Unstoppable. Selecting one is a micro-commitment, not a setting.
  7. Plan building — animated percentage 0→100% with staged status lines ("Analyzing your responses…", "Matching drills…") and rotating testimonials underneath. Takes ~5–8 seconds on purpose.
  8. Plan ready — confirmation screen ("Your plan is unlocked") with a single Continue.
  9. Notification permission — asked here, with context (a mock notification preview: "Log a drill today"), and an "I'll do it later" escape. Never at app launch.
  10. Paywall — free-trial timeline: three rows (Today — unlock everything / Day X — reminder before trial ends / Day Y — billing starts), monthly vs yearly price cards with yearly pre-selected and a "X days free" chip, "✓ No Payment Due Now" reassurance line, CTA "Try for $0.00" or "Start my X-day free trial", fine print with real price under the button. A reminder-bell interstitial ("We'll send you a reminder before your trial ends") can precede it.
  11. Account creation — after the paywall: Sign in with Apple first, email fallback. Then into the app.

Rules

  • The quiz data must actually drive something: the personalized claim, the plan contents, or at minimum the copy. A quiz that changes nothing reads as fake and belongs cut.
  • One question per screen, always. Never stack questions.
  • Skips: the quiz has no skip; notifications and account creation do.
  • Keep the funnel in its own route group (app/onboarding/) with completion flags persisted, so restarts resume rather than repeat.
  • In the spec's Build order, the funnel is its own slice, built after the core feature works — the app must be worth onboarding into first.
  • Trial mechanics, prices, and durations go in the spec as concrete values, not placeholders.
example-spec.mdA full worked spec to match the shape and detail.

Forge — build spec (worked example)

This is the shape and level of detail a spec should have. Match the concreteness, not the content.

Pitch

A gamified daily-discipline tracker: complete your tasks, earn XP, rank up, and compete with friends.

Users and the core job

Self-improvement-minded users (16–30) who open the app each morning to check off the day's tasks and watch their rank grow.

Scope

In scope (v1)

  • Create, edit, complete, and delete daily tasks with a category and an XP value
  • Earn XP on completion; level up through named rank tiers with a visible progress ring
  • Daily streak that increments when at least one task is completed
  • Badge gallery with earned/locked states
  • Friend leaderboard ranked by XP, with invites via share link

Out of scope (v1)

  • Social feed, comments, or chat
  • Custom task schedules (weekly/monthly recurrence)
  • Android-specific widgets, watch app, push campaigns

Stack

  • Framework: Expo (React Native + TypeScript) — one codebase, fast iteration
  • Navigation: Expo Router, tabs + modals
  • State: Zustand for session state; TanStack Query for server data
  • Backend: Supabase — auth, Postgres, row-level security
  • Storage: AsyncStorage for onboarding flags only; all data server-side
  • Styling: NativeWind
  • Other services: none in v1 (RevenueCat deferred to v2 paywall)

Assumptions

  • Email + Apple sign-in are enough; no Google login in v1.
  • XP values are fixed per category (workout 200, study 150, chore 50) rather than user-set.
  • Leaderboard is friends-only, no global board.

Screens

  • Home (/) — XP ring around current rank badge, level + rank name, streak flame in top bar, today's task list, "+ Add task" pill. Actions: complete task, open add-task sheet, open task detail.
  • Tasks (/tasks) — full task list grouped by day, swipe to delete.
  • Leaderboard (/leaderboard) — top-3 podium, ranked friend rows, "+ Invite Friends".
  • Badges (/badges) — grid of badge slots, earned vs. dimmed locked.
  • Profile (/profile) — avatar, lifetime stats, sign out.
  • Add task (modal sheet over Home) — title, category picker, shows XP value.
  • Auth (/auth) — sign in / sign up, shown when logged out.

Navigation

5-tab bar: Home, Tasks, center pill (Add task shortcut), Leaderboard/Badges, Profile. Entry point: Home. Auth stack replaces tabs when logged out.

Data model

  • User — id: uuid, handle: string, avatar_url: string, xp: int, level: int, streak: int, last_completed_at: date; stored in Supabase users.
  • Task — id: uuid, user_id: fk, title: string, category: enum, xp_value: int, completed_at: timestamp|null, date: date; stored in Supabase tasks.
  • Badge — id: string, name: string, requirement: string; static table. UserBadge — user_id + badge_id + earned_at.
  • Friendship — user_id, friend_id, created_at. User 1—N Task; User N—N Badge; User N—N User via Friendship.

User flows

  1. Morning check-off: open app → Home shows today's tasks → tap checkbox → check fills, "+200 XP" toast, ring animates → if threshold crossed, level-up moment (new badge scales in) → streak increments on first completion of the day.
  2. Add task: tap "+ Add task" → sheet slides up → enter title, pick category → Save → task appears at top of list.
  3. Invite: Leaderboard → "+ Invite Friends" → native share sheet with deep link → friend signs up → both appear on each other's board.

Backend / API

Supabase tables as above with RLS: users read/write own rows; tasks scoped to owner; leaderboard reads friends' user rows (xp, level, handle, avatar only). Operations: CRUD tasks, increment xp/streak on completion (Postgres function to keep it atomic), fetch friend board ordered by xp desc.

Design direction

Follows references/design-language.md in full: charcoal #0C0F0E background, mint-emerald #2EE59D single accent, emerald→black hero gradients, system font with green stat numerals, 3D metallic rank badges with dimmed locked states, XP ring as the home hero, podium leaderboard, 5-tab bar with center pill. Motion per the apple-design skill: critically damped springs, press-down feedback, interruptible sheets; drama reserved for task completion (ring + XP count-up) and level-up (badge scale-in with glow). Reduced-motion falls back to cross-fades.

Build order

  1. Scaffold: Expo + Router + NativeWind, tab shell with empty screens, dark theme tokens. App runs.
  2. Supabase project, auth screens, session handling. Login round-trip works.
  3. Tasks end to end: schema, Home list, add-task sheet, complete/delete, XP increment.
  4. Rank system: XP ring, levels, rank names, level-up animation.
  5. Streak logic + flame in top bar.
  6. Badges: static definitions, earning checks, gallery grid.
  7. Leaderboard: friendships, invite deep link, podium + rows.
  8. Polish pass: spring motion, haptics on completion, reduced-motion, empty states.

Acceptance criteria

  • Tasks: can create, complete, and delete a task; completion persists across restart.
  • XP/rank: completing tasks visibly fills the ring; crossing a threshold shows the level-up moment and the new badge.
  • Streak: completing a task on consecutive days increments the flame count; skipping a day resets it.
  • Badges: an earned badge renders full-color; others render dimmed.
  • Leaderboard: two accounts that friend each other see each other ranked by XP.

Open questions

None.
